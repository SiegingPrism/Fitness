8. Automatic Token Refresh
When API returns:
401
the client should:
Request
 ↓
401
 ↓
Refresh token
 ↓
New access token
 ↓
Retry original request
Important:
If 10 requests fail simultaneously, don't send:
10 refresh requests
Instead use a single refresh operation and queue the failed requests behind it.
Request A ─┐
Request B ─┤
Request C ─┤
           ▼
      One refresh
           │
           ▼
      New token
           │
      ┌────┼────┐
      ▼    ▼    ▼
      A    B    C
This avoids race conditions.

# 4J.2 — Environment Configuration

We need three environments:

```text

     ↓
Staging
     ↓
Production
```

Never use production MongoDB credentials during local development.

```text
.env.development
.env.staging
.env.production
```

Variables should include things such as:

```text
NODE_ENV
PORT
MONGODB_URI
JWT_SECRET

WEBSOCKET_URL
```

Secrets must never be committed to Git.

# 4J.3 — Centralized Configuration

Create:

```text
server/src/config/env.ts
```

Instead of doing this throughout the application:

```ts
process.env.MONGODB_URI
process.env.JWT_SECRET
process.env.PORT
```

use:

```ts
config.database.mongoUri
config.auth.jwtSecret
config.server.port
```

Then validate the environment **when the server starts**.

If MongoDB credentials are missing:

```text
Server startup
     ↓
Environment validation
     ↓
Missing MONGODB_URI
     ↓
FAIL IMMEDIATELY
```

rather than discovering it 20 minutes later when an API request fails.

# 4J.4 — Global Error Handling

Every API should return a predictable structure.

Success:

```json
{
  "success": true,
  "data": {}
}
```

Error:

```json
{
  "success": false,
  "error": {
    "code": "ATHLETE_NOT_FOUND",
    "message": "Athlete could not be found"
  }
}
```

Don't return random structures such as:

```json
{
  "error": "something went wrong"
}
```

from one endpoint and:

```json
{
  "message": "Not found"
}
```

from another.

# 4J.7 — Database Index Audit

Since we're using MongoDB, this becomes important now.

Indexes should exist for common queries.

For example:

```text
users
 └── email

organizationMemberships
 ├── organizationId
 ├── userId
 └── organizationId + userId

workoutSessions
 ├── athleteId
 ├── athleteId + startedAt
 └── workoutId

messages
 ├── conversationId + createdAt
 └── senderId

notifications
 ├── recipientId + createdAt
 └── recipientId + readAt
```

Don't create indexes blindly.

Each index has a storage and write-performance cost.

# 4J.8 — Query Audit


Instead:

```text

Batch required data
       ↓
Return response
```

This matters especially for the Coach Dashboard and Admin Dashboard.

# 4J.14 — Retry Strategy

Don't retry everything indefinitely.

For temporary failures:

```text
Attempt 1
 ↓
wait
 ↓
Attempt 2
 ↓
wait
 ↓
Attempt 3
 ↓

```

Use exponential backoff for appropriate requests.

Never blindly retry mutations that could create duplicate records.

# 4J.15 — Idempotency


```text

```

for the same action.

Use an idempotency key where appropriate:

```text

```

Backend:


# 4J.18 — MongoDB Security Rule

Never trust IDs coming from the client.

Bad:

```ts
findOne({
  _id: athleteId
});
```

Better:

```ts
findOne({
  _id: athleteId,
  organizationId: currentOrganizationId
});
```

And for coaches:

```ts
verifyCoachAthleteRelationship(
  coachId,
  athleteId
```

**Authorization must happen before returning data.**

# 4J.37 — Database Migration Strategy

Even with MongoDB, schemas evolve.

Don't simply change code and hope old documents work.

Use:

```text
Schema Version
```

where necessary.

Example:

```text
Workout
schemaVersion: 2
```

Then migrate old documents safely.

# 4J.38 — API Versioning

Keep:

```text
/api/v1/...
```

We've already been following this.

When breaking changes become necessary:

```text
/api/v2/...
```

Don't suddenly change:

```text
/v1
```

and break every older mobile client.
